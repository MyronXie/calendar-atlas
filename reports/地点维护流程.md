# 地点维护流程（固化版）

本文件把地点库的两种常规操作固化下来，便于定期、可复现地维护 `user-data/place.csv`。

## 0. 数据与约定
- 主库 `user-data/place.csv`，列：`location,address,adcode,lat,lon,firstShown,lastShown,valid,type,labels,aliases`
- `location`：主名称；`aliases`：旧名/别名（分号分隔），匹配时与 `location` 等同
- `adcode`：6 位行政区划码（消歧用；境外留空）
- 日期格式统一 `YY/MM/DD`（如 `26/11/17`）
- `valid`：`YY/MM/DD`=该日核验在营；`no`=停业；`skip`=本轮未确认、待下次验证（流程二会继续核验，不跳过）；空=未核验
- `firstShown` / `lastShown`：日历中该地点首次/最后一次出现的日期
- 坐标系统一按 GCJ-02 处理（高德返回即 GCJ-02）
- 匹配身份 = **括号前的品牌核心**；括号（`(...)`）通常是商场/分店，不作为身份依据

## 1. 通用匹配规则（两流程共用）
1. 归一化：NFKC、小写、去标点/空白。
2. **直接匹配**：日历地点与 `location` 或任一 `aliases` 归一化后相等。
3. 地图校验（未直接匹配或需复核时）：
   - 多源：**高德**（`place/text`+`city=adcode&citylimit=true`、`place/around`、`geocode/regeo`）为主，**百度**（`map.baidu.com/?qt=s`）为辅。
   - 判定顺序：完全同名 → 品牌核心相似（连续公共子串≥0.6）→ 同商场且核心近似（≥0.45 且≤60m）→ 近址同名/同品牌 → 否则停业倾向。
   - 候选需结合名称、地址、类型、距离综合判断；勿只凭单一关键词。
4. 只改 `location/aliases/coordinates/adcode/type/labels/firstShown/lastShown/valid`，不改无关行。

## 2. 流程一：日历更新后同步地点
触发：`calendar.ics` 有更新。
步骤：
1. **读取日历**：解析所有事件 `LOCATION` 与正文 `Place：` 行，得到去重地点及其首次/最后出现日期。
2. **匹配主库**：对每个日历地点，用 `location`+`aliases` 直接匹配。
3. **未匹配的走地图校验**：高德/百度检索，给出建议（三类）：
   - `直接匹配`（其实已在库）
   - `改名后匹配` → 建议新名称 + 坐标 + adcode（旧名将入 alias）
   - `无法匹配`（附候选，供人工判断）
4. **生成 md 报告** + **决策 csv 模板**（不下写主库）。
5. **用户反馈**后，用 apply 脚本写入：
   - 改名匹配：旧名→`aliases`，`location`=新名，更新 `lat/lon/adcode/type/labels`
   - 直接匹配/新增：补 `firstShown/lastShown`（按日历计算），`valid`=当天日期
6. 命令：
   ```
   $env:AMAP_KEY=...; node tools/place-sync.mjs
   # 生成 reports/日历地点同步报告_<YYYYMMDD>.md 与 reports/日历地点同步_决策_<YYYYMMDD>.csv
   # 用户确认后：
   node tools/place-apply.mjs --decisions reports/日历地点同步_决策_<YYYYMMDD>.csv --mode sync
   ```

## 3. 流程二：周期性有效性核验
触发：每过一段时间（建议每 1–3 个月）。
跳过规则（先剔除）：`valid=no` 的跳过；`valid` 为日期且距今天 **< 3 个月（90 天）**的跳过。
步骤：
1. 读取主库，按上面规则筛出“需复核”的地点（valid 为空或日期已超 3 个月）。
2. 高德/百度校验：判断 存在 / 疑似改名 / 疑似停业；**境外地点改用 OSM/Photon（反查+检索）**。
3. 生成 md 报告 + 决策 csv 模板。
4. 用户反馈后 apply：
   - 存在 → `valid`=当天
   - 改名 → 旧名入 alias、改 location/坐标、`valid`=当天
   - 停业 → `valid=no`
5. 命令：
   ```
   $env:AMAP_KEY=...; node tools/place-verify.mjs --months 3
   # 生成 reports/地点有效性核验报告_<YYYYMMDD>.md 与 ..._决策_<YYYYMMDD>.csv
   node tools/place-apply.mjs --decisions reports/地点有效性核验_决策_<YYYYMMDD>.csv --mode verify
   ```

## 4. 决策 CSV 格式
```
location_old,action,new_name,lat,lon,adcode,note
某店(旧名),rename,新店名,31.23,121.47,310115,改名匹配
旧店,closed,,, ,,停业
某点,keep,某点,31.23,121.47,310115,直接通过
```
`action`：`rename`/`closed`/`keep`（keep 表示更新 valid 为当天，名称不变）。

## 5. 文件命名约定
- 同步报告：`reports/日历地点同步报告_<YYYYMMDD>.md`；决策：`reports/日历地点同步_决策_<YYYYMMDD>.csv`
- 核验报告：`reports/地点有效性核验报告_<YYYYMMDD>.md`；决策：`reports/地点有效性核验_决策_<YYYYMMDD>.csv`
- 每次 apply 前自动备份到 `user-data/.backups/`

## 6. 注意事项
- `checked` 临时列已在核验完成后删除；状态统一看 `valid`。
- 含空格的英文/混合地名：在日历 `Place：` 里用引号包裹（`"…"`、`“…”`、`「…」`），解析器会整段视为一个地点、并去掉引号，避免按空格拆开。
- 高德 Key 通过环境变量 `AMAP_KEY` 传入，不写入库文件。
- 多子点/多城同名（如“上海东方体育中心/南京东路/荟聚”）无法唯一确定时，报告标注“歧义”，留待人工/语义择一。
- 关键词/字符串相似只是召回，最终判断应结合名称语义、地址、类型、距离，必要时人工确认。
