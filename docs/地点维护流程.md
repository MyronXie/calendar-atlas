# 地点维护流程（名称匹配 + SOP）

地点主库为 `atlas-data/place.csv`。本文合并了「操作流程（脚本优先）」与「名称匹配规则」。原则：**机械与规则判断交给脚本，人只处理少量例外**；每次写入前脚本会自动备份到 `atlas-data/.backups/`。

## 一、标准流程（按顺序）

### 1. 本地体检（不联网）
```powershell
npm run audit
```
产出 `temps/日历内容整理检查.md`（格式问题、缺坐标清单），已按 `config.json` 黑名单过滤。

### 2. 日历地点同步（联网）
```powershell
$env:AMAP_KEY='<高德Key>'   # 仅在高德兜底时需要
npm run sync                      # 默认：百度优先，百度无精确/低置信才用高德
npm run sync -- --no-amap         # 完全不用高德
npm run sync -- --max-amap 20     # 最多用 20 次高德关键字
```
产出：
- `temps/日历地点同步报告_<日期>.md`
- `temps/日历地点同步_候选_<日期>.csv`（候选，含 `confidence/source/matched_by`）
- `temps/地点待人工匹配_<日期>.csv`（低置信 + 未匹配）

**检索顺序：先百度（免费），后高德。** 只有百度没有“精确同名”且最高相似度低于 `--high`（默认 0.90）时，才调用高德关键字；高德额度不足会用 `--no-amap` / `--max-amap` 控制并记录。

### 3. 生成待确认候选（补字段）
```powershell
npm run screen -- --decisions "temps/日历地点同步_候选_<日期>.csv"
```
产出 `temps/地点候选_待确认_<日期>.csv`：已补齐 `firstShown/lastShown`（按日历，含重复事件展开）、`valid=今天`、`type/labels`，并带 `confirmed=no`、`source`、`confidence`。
- **所有候选都必须由用户逐条确认**（把 `confirmed` 改成 `yes`，或告诉脚本保留哪些）。
- 例外仍可用 `atlas-data/place-overrides.json`（`accept/reject/keepOriginal`）批量处理同名不同店/城市的情况。

### 4.（可选）补地址与 adcode
```powershell
$env:AMAP_KEY='<高德Key>'
npm run enrich -- --rows "temps/地点候选_待确认_<日期>.csv" --write
```
缺 `address` 用百度补（免费）；缺 `adcode` 用高德**逆地理编码**补（额度独立且充足）；境外无 adcode 留空。此步可选。

### 5. 用户逐条确认
在 `temps/地点候选_待确认_<日期>.csv` 中把要加入的行 `confirmed` 改为 `yes`（删掉不要的行也可以）。

### 6. 合并写入 + 分类 + 排序
```powershell
npm run merge -- --rows "temps/地点候选_待确认_<日期>.csv" --sort firstShown --write
```
脚本默认**只写入 `confirmed=yes` 的行**（`--all` 才会全部写，慎用）；并补 `type/labels`、按 `firstShown` 排序、备份后原子写入。

### 7. 生成报告 + 验证
```powershell
npm run report -- --candidates "temps/地点候选_待确认_<日期>.csv" --manual "temps/地点待人工匹配_<日期>.csv"
npm test
```
报告 `temps/地点匹配报告_<日期>.md` 汇总候选与待人工项，便于留档。

## 二、高德额度策略
- **正常顺序：先百度，后高德。** 百度免费、先用；高德只在百度没有精确同名结果时兜底。额度紧张时给 `npm run sync` 加 `--no-amap`。
- 本次实践中出现的“高德定向复核”属于非常规操作，原因是百度自动匹配错误较多且高德额度有限，只能少量定点查询。
- **关键字搜索 / 周边搜索**共用额度，接近上限时不要使用。
- **逆地理编码**额度独立且充足，只用于补 `adcode` / 行政区地址（`npm run enrich`）。

## 二之二、其他可用的免费地图服务
- **百度地图网页检索（当前使用）**：无需 Key，但属非官方接口，稳定性和字段有限（无 adcode）。
- **OpenStreetMap Nominatim**：免费逆地理/搜索，需遵守使用频率与 User-Agent 政策，适合境外。
- **Photon（Komoot）**：免费搜索/逆地理，境外覆盖较好（项目已在 `place-common` 使用）。
- **Overpass API**：免费查 OSM 要素（POI/边界），适合精确几何，不宜高频。
- **天地图 / 腾讯位置服务**：需申请 Key，有免费配额，境内 POI/行政区较正规。
- **高德**：需 Key，有免费配额，关键字/周边搜索额度有限，逆地理额度较充足。
策略：境内默认百度，失败再高德；境外优先 OSM/Photon；需要 adcode 用高德逆地理。

**本机实测（8 个境内地点）**：
- **Photon**：名称检索可用（多数能命中且名称相似度高），但坐标偏移约 350–660 米；逆地理只返回街道/建筑名，不能直接当 POI。适合做“名称/别名候选”，不适合取精确坐标。
- **Nominatim**：本机网络请求全部失败（不可达），当前环境无法作为兜底；网络可用时可再评估，但中文 POI 覆盖通常弱于百度/高德。
- 结论：境内仍以**百度为主、高德兜底**；Photon 仅在境外或“名称候选”场景辅助使用。

## 三、字段
| 字段 | 含义 |
| --- | --- |
| `location`、`aliases` | 主名称和用分号分隔的别名 |
| `address`、`adcode` | 地址和六位行政区划码，境外行政区划码可留空 |
| `lat`、`lon`、`datum` | 纬度、经度和坐标系。高德返回 GCJ-02 |
| `firstShown`、`lastShown` | 日历首次和最后一次出现的日期，格式为 `YY/MM/DD` |
| `valid` | 日期表示上次核验在营，`no` 表示停业，`skip` 或空值进入下次核验 |
| `type`、`labels` | 地点分类和以分号分隔的标签 |

## 四、名称匹配规则

### 日历与地点库
程序读取事件的 `LOCATION` 和备注中的 `Place：` 行。地点工具用 `place.csv` 的 `location` 和 `aliases` 匹配，比较前进行 NFKC 归一化、转小写并移除标点与空白（见 `lib/place-name.js` 的 `loose`）。日历仍可使用登记过的别名。

地图候选的品牌相似度取括号前的名称，以最长连续公共子串除以较短核心的长度。括号常用于区分分店，核对时要同时看完整名称、商场、行政区、地址和距离。

### 日历地点同步
先按名称或别名匹配主库；未命中时**先百度**检索召回候选，百度无精确同名时才用高德兜底。归一化名称完全匹配的候选进入新增清单，品牌相似度 ≥0.6 的进入改名核对清单，其余列在报告中供确认。

### 地点有效性核验
国内地点用高德和百度检索名称，并搜索原坐标附近 80 米 POI。完全同名、附近同名或品牌相似度 ≥0.7 时建议保留；名称不同且品牌相似度 ≥0.6 时建议核对改名；附近 60 米有其他候选时列为疑似停业，其余进入人工核验。境外候选使用 OSM/Photon 的名称搜索与逆地理编码，结合距离与名称判断。建议改名或停业时，先用门牌、商场或近期公开资料确认。

## 五、定期核验营业状态
1. 运行 `npm run verify -- --months 3`。脚本跳过已停业记录和最近 90 天核验过的记录；阈值按每月 30 天计算。
2. 核对当天生成的报告和 `地点有效性核验_决策_<日期>.csv`：仍营业用 `keep`，改名用 `rename`，已停业用 `closed`；资料不足可移除决策行留待下次。
3. 按实际文件名执行写回，写入前在 `atlas-data/.backups/` 保存副本。

```powershell
npm run apply -- --mode verify --decisions "temps/地点有效性核验_决策_<日期>.csv"
```

## 六、决策表格式
```csv
location_old,action,new_name,lat,lon,adcode,note
新地点,add,新地点,31.23,121.47,310115,确认新增
原店名,rename,新店名,31.23,121.47,310115,确认改名
正常营业地点,keep,,,,,更新核验日期
已停业地点,closed,,,,,确认停业
```
`rename` 会保留原名称用于匹配日历；`keep` 和 `rename` 会把营业核验日期更新为当天。地址、分类、标签与坐标系也可在 **设置 → 地点管理** 维护。

## 七、脚本清单
| 命令 | 脚本 | 作用 |
| --- | --- | --- |
| `npm run audit` | `tools/audit-calendar.mjs` | 日历体检、缺坐标清单 |
| `npm run sync` | `tools/place-sync.mjs` | 日历→地点同步，输出报告+决策 CSV（含 sim/address） |
| `npm run screen` | `tools/place-screen.mjs` | 按相似度+例外清单筛选，产出可合并行 |
| `npm run enrich` | `tools/place-enrich.mjs` | 百度补地址、高德逆地理补 adcode |
| `npm run classify` | `tools/place-classify.mjs` | 单独补 `type/labels`（默认只补空值） |
| `npm run merge` | `tools/place-merge.mjs` | 合并**已确认**候选行、补分类、按 firstShown 排序、备份写入 |
| `npm run report` | `tools/place-report.mjs` | 汇总候选与待人工清单为报告 |
| `npm run verify` | `tools/place-verify.mjs` | 定期核验营业状态（只读产出） |
| `npm run apply` | `tools/place-apply.mjs` | 应用决策 CSV（sync/verify 两种模式） |
| `npm run pending` | `tools/refresh-pending-places.mjs` | 生成待补坐标清单 |

## 八、回滚
`atlas-data/.backups/place.csv.<时间戳>.<uuid>.bak` 为每次写入前快照，复制回 `atlas-data/place.csv` 即可。

照片地点提取和日常区域排除见 [使用说明](使用说明.md#从照片提取地点行程)。
